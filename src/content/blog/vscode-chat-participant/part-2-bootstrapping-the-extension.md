With the skill defined, the next step is a home for it. This part is the least glamorous and the most important: getting the toolchain right so that everything in Parts 3–6 compiles, bundles, and tests cleanly.

## Dogfooding the skill

A small but satisfying detail: the bootstrap objective itself was generated by the very skill we'd just built. I fed the prompt-refiner a rough request — *"bootstrap a VS Code plugin which will include a chat participant with prompt-refiner skill and also make language model API calls with GitHub Copilot Chat"* — and used its structured output as the spec. It's a nice closed loop: the thing we're building helps build itself.

## The scaffold

The extension is a standard VS Code extension with a deliberately boring set of defaults:

- **Package manager:** npm
- **Module system:** TypeScript → CommonJS, bundled with **esbuild**
- **Test runner:** `@vscode/test-cli` (+ `@vscode/test-electron`, mocha)
- **Engine/API:** VS Code `^1.90.0` — the first stable release of the `vscode.chat` and `vscode.lm` APIs this whole series depends on

The `package.json` scripts tell the story:

```json
"scripts": {
  "vscode:prepublish": "npm run package",
  "compile": "npm run check-types && node esbuild.js",
  "watch": "npm-run-all -p watch:*",
  "watch:esbuild": "node esbuild.js --watch",
  "watch:tsc": "tsc --noEmit --watch --project tsconfig.json",
  "check-types": "tsc --noEmit",
  "package": "npm run check-types && node esbuild.js --production",
  "compile-tests": "tsc -p . --outDir out",
  "pretest": "npm run compile-tests && npm run compile",
  "test": "vscode-test"
}
```

Two things to note. First, **esbuild** produces the production `dist/extension.js` (the `main` entry point), while `tsc --noEmit` is used only for type-checking — the two responsibilities are cleanly separated. Second, the `npm-run-all -p watch:*` command runs the esbuild watcher and the type-check watcher *in parallel* during development, so you get rebuilds *and* type feedback simultaneously.

## The manifest: what the extension contributes

The heart of any VS Code extension is its `contributes` block in `package.json`. Ours declares three things — the participant, palette commands, and configuration:

```json
"contributes": {
  "chatParticipants": [
    {
      "id": "chat-participant-tutorial.cleveloper",
      "name": "cleveloper",
      "fullName": "Cleveloper",
      "description": "A chat participant (@cleveloper) that answers via Copilot Chat and can refine raw prompts into structured prompts.",
      "isSticky": true,
      "commands": [
        { "name": "refine", "description": "Refine a raw prompt into a structured prompt." },
        { "name": "snippets", "description": "List saved snippets and return one." }
      ]
    }
  ],
  "commands": [
    { "command": "cleveloper.refine", "title": "Cleveloper: Refine Prompt", "category": "Cleveloper" },
    { "command": "cleveloper.snippets", "title": "Cleveloper: Insert Snippet", "category": "Cleveloper" }
  ],
  "configuration": {
    "title": "Cleveloper",
    "properties": {
      "cleveloper.refine.preferredModel": {
        "type": "string",
        "default": "",
        "markdownDescription": "Preferred model for the prompt-refiner (/refine). Matched case-insensitively against each model's vendor, family, or name. Leave empty to auto-select the cheapest available model."
      }
    }
  }
}
```

Three details worth calling out:

- `isSticky: true` keeps `@cleveloper` pinned in the participant picker so users don't have to hunt for it.
- The participant declares `commands` (`/refine`, `/snippets`) — the slash-command surface VS Code renders as suggestions in the Chat view.
- The `configuration` block is how we expose a user-facing setting. It's already wired to the model-selection story we'll build in Part 3.

## The rename: @participant → @cleveloper

The scaffold originally produced a generic `@participant`. The first real product decision was a name, and it ripples through *every* layer:

- `package.json` — the participant's `name`, `fullName`, and `description`
- The participant's **id** — `chat-participant-tutorial.cleveloper`
- The source constant — `PARTICIPANT_ID`
- The `/refine` hint text and the README

A participant's id is its identity: it's what users type after `@` and what your request handler matches on. Picking a good one early is worth it, because renaming later means touching manifest, source, and docs together — which is exactly the kind of cross-cutting change that's easy to get subtly wrong.

## The entry point

`src/extension.ts` is where everything wires up:

```ts
export function activate(context: vscode.ExtensionContext): void {
  createParticipant(context);
  registerRefineWebview(context);
  registerSnippetsCommand(context);
}
```

At this point only the participant exists (the webview and snippets come in Parts 4 and 5), but the shape is already visible: `activate` is a list of registrations, each owned by its own module. That structure — thin `extension.ts`, thick feature modules — is what keeps the extension maintainable as we add features.
